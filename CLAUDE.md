This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

This is not a codebase. It is Uriah Raffer's working folder for applying to California state IT jobs through CalCareers. The work here is producing application materials: tailored resumes, Statements of Qualifications (SOQs), and STD 678 application content for specific job postings.

Consult it before asking Uriah to re-explain anything. ## Folder structure and conventions

- Each job application gets its own folder, tagged with status: `JC-###### (Title) - IN-PROGRESS/` while being worked, renamed to `JC-###### (Title) - SUBMITTED/` once filed. Postings Uriah decides to pass on are **deleted entirely** — only IN-PROGRESS or SUBMITTED folders should ever be visible. Each folder holds the job posting PDF, the duty statement PDF, and the tailored deliverables.
- Deliverables are named `Uriah_Raffer_<Doc>_JC-######` (e.g., `Uriah_Raffer_Resume_JC-520957.docx`). Produce both .docx and .pdf versions.
- New postings to evaluate are surfaced by the **CalCareers Job Scraper** project (`../CalCareers Job Scraper/data/jobs/`), not found manually. When triaging multiple candidates, present them to Uriah one job at a time to avoid confusion.
- Root-level files are shared source material reused across applications.

## Working rules

1. **New application:** create the `JC-###### (Title)/` folder, save the posting and duty statement PDFs into it, then tailor the resume and SOQ against the duty statement and the SOQ prompt in the posting.
2. **SOQ workflow:** follow the process in `SOQ Research/soq-writing-guide.md` — get the actual prompt and page/word limit, ask Uriah for the real specifics (situation, tools, numbers, outcome), draft with STAR, then check the draft against the anti-AI checklist before calling it done.
3. **Never fabricate experience — including tools.** Everything must trace back to `Employment_History_STD678.md`, the base resume, or facts Uriah supplies in conversation. Self-employment (options trading, online business) was deliberately removed from applications — do not reintroduce it. **Never claim hands-on experience with any tool, software, OR specific skill/duty Uriah has not actually done**, on the resume, SOQ, or 678 — even when the duty statement names it. A named tool, skill, or duty is exactly what a screener probes at interview. This is NOT just product names: do not stretch an adjacent real experience into a duty he hasn't earned. Examples pulled on JC-521522: VMware ESXi (he uses Proxmox for Type 1; only VMware Workstation/Hyper-V/VirtualBox for Type 2); ServiceNow (never used); and "resolving Windows security update issues" (the duty means troubleshooting a broken Windows Update mechanism, which he has never done — remediating outdated software in the vuln-management project is NOT the same thing). Represent the real adjacent experience instead; in the SOQ/cover letter it is fine to argue transferable competence and fast ramp-up, which claims learnability, not fictional experience. When tailoring, scan for tool/product names AND duty wording that implies specific troubleshooting, and verify each before leaving it in; ask Uriah if unsure.
4. **Formatting constraints for CalCareers fields:** under ~1,000 characters per Duties Performed block (the box clips beyond that), no em dashes, no mid-sentence colons.
5. SOQs typically must follow the exact format the posting demands (page limit, font, numbered responses to each prompt) — check the posting's SOQ instructions every time; failure to follow them disqualifies the application. Verify the built SOQ fits the page limit by converting to PDF and checking the page count before calling it done.
6. **Cert slots on the STD 678 hold only three.** The Licenses section fits three certifications. Pick the three most relevant to the role (A+, Network+, Security+ for help-desk/support roles; swap Cloud+ in for cloud- or security-heavy roles). All four CompTIA certs always stay on the resume regardless.
7. **Writing rules for everything submitted under Uriah's name (SOQ, 678, resume):**
   - **Mirror the duty statement's exact language** in both the 678 Duties Performed blocks and the SOQ, so the screening keywords match.
   - **Spell out every acronym on first use** (e.g., "Domain Name System (DNS)"), then abbreviate — the panel often includes non-technical HR readers who score these. **This applies to the SOQ and STD 678 only. The resume is EXEMPT** (Uriah confirmed) — common IT acronyms (IT, DNS, DHCP, AD, TCP/IP, VLAN, SLA, etc.) can appear bare on the resume; do not over-expand them there.
   - **Avoid cross-document copy/paste.** Reuse the same real experiences across the resume, SOQ, and 678, but vary the wording and use different examples so no two documents read like a paste. After drafting all three, do a redundancy pass: differentiate duplicated anecdotes and reword repeated stock phrases.
   - **Do not lean on ITIL 4.** Never anchor a skill or claim on the ITIL 4 cert in prose (SOQ, cover letter, 678) — Uriah can't speak to it and wouldn't survive an interview probe on it. It can stay in the certifications LIST only. Frame ticketing/SLA/service-management familiarity on real work, not the cert.
   - **No mid-sentence colons.** Colons only introduce a list (formatted or a short inline series). Never use a colon mid-sentence before a single explanatory clause or example. E.g. avoid "if you use a colon, then follow it with a list" style mid-sentence colons — restructure with a period or comma.
8. **Honest-fit triage.** Only pursue roles that are a genuine, defensible technical fit. "Applying up" (e.g., a new grad applying to a role pitched at an experienced candidate) is fine as long as every claim is truthful. Do not gate an application on a tool Uriah lacks when the role only uses it at a basic level (e.g., ServiceNow for a service desk that just logs tickets in it) — apply honestly without claiming it. Pass on roles whose core identity is a real skill gap (e.g., database administration, physical-security platforms).
9. **Keep the progress log current automatically.** After any application activity (drafting or revising an SOQ, resume, cover letter, or STD 678; reviewing and deciding to pass), update `PROGRESS_LOG.md` (newest day first) and the relevant tracking record (the per-JC folder, or `Non-State Applications/` for private-sector apps) without being asked. Record the date, the job, the status, and any issues or decisions.
10. **Post-submission routine.** The moment Uriah says an application is submitted, do all four without being asked: (a) rename the folder from `- IN-PROGRESS` to `- SUBMITTED`; (b) save the uploaded STD 678 into that folder as `Uriah_Raffer_STD678_JC-######.pdf`; (c) update `PROGRESS_LOG.md`; (d) write an `Interview_Prep_JC-######.md` into the SUBMITTED folder capturing the 2 to 3 things a panel will most likely probe and how Uriah would answer each (the real gaps for that role plus the gap-handling framing, and his 2 to 3 strongest talking points). He submits in volume and interviews can come weeks later when the context is cold, so this gives him the landmines mapped in advance. Keep it honest and specific to that posting, and reuse the gap framings already in MEMORIES.md.
11. **Sandbox file-lock when regenerating documents (IMPORTANT — wasted a whole resume cycle on JC-521522).** Once a `.docx`/`.pdf` has been written to the outputs scratchpad, the sandbox often will not let you overwrite it (`rm`/rewrite returns "Operation not permitted"). When that happens, a rebuild silently writes nothing and the subsequent PDF conversion just re-renders the STALE old file — so the page count never changes no matter how much you edit, and you wrongly conclude your content cuts "weren't enough." Rules: (a) treat "output did not change after a real edit" as a FILE-WRITE failure, not a content problem — stop editing content and check the file; (b) when iterating on a doc, build to a NEW filename each time (e.g. `_v2`), or verify the file's modified-time actually advanced before trusting any render; (c) do the page-count check against the freshly written file, not a chained re-convert of a possibly-locked one; (d) copy the final good file into the per-JC folder under its proper `Uriah_Raffer_<Doc>_JC-######` name once verified. Also: the Write/Edit tools sometimes emit the build script as UTF-16 with null bytes — if `node` throws "Invalid or unexpected token," strip nulls before blaming the code. **BEST PRACTICE that avoids the lock dance entirely (adopted 2026-06-20): do ALL drafting and iteration in the outputs scratchpad and present from there; copy into the per-JC folder ONCE, the final approved version, after the doc is signed off. Copying every draft into the live folder is what causes the "Operation not permitted" churn, because Uriah often has the file open in a viewer.** Also: Claude creates the upload PDF via the docx->LibreOffice flow (renders as LiberationSans, which is visually Arial and accepted by Uriah). Do NOT use the Google Drive MCP connector to export documents — it round-trips files as base64 and is far slower than the docx->LibreOffice PDF flow.
12. **Canonical memory is `MEMORIES.md` in the project root.** It is imported into CLAUDE.md, so it loads every session. Read it before asking Uriah to re-explain anything. When he shares an experience, a real tool he has used, or a settled decision, append a dated entry there (newest first in the Experience log) without being asked. Keep it honest — only record what Uriah himself has actually done. Prefer this file over Claude's built-in auto-memory store.
13. **Always start a recurring deliverable from the latest SUBMITTED version — never from the base file or from scratch.** Before producing a resume, SOQ, STD 678, or cover letter, FIRST open the most recent `Uriah_Raffer_<Doc>_JC-######` in a `- SUBMITTED` folder and use it as the template for BOTH formatting (house style) and content density, then tailor the content to the new posting. Do NOT rebuild from the plain base resume and do NOT generate fresh formatting. **Resume house style is CALIBRI — this is settled (Uriah confirmed 2026-06-20). Clone the CLOSEST-ROLE Calibri-lineage submitted resume as the template — role match beats recency (proven 2026-06-24: the server-focused `Uriah_Raffer_Resume_JC-521435` was the right clone for the CHP server-admin role JC-522483, NOT the latest support-forward resume). Calibri-lineage sources by lane: `JC-521435` for server/sysadmin/security, `JC-522278` / `JC-522217` for ITA support/service-desk.** Do NOT clone the Arial-lineage resumes (e.g. JC-522094, JC-521631, JC-521522) even if one is technically the most recent submission — they are a dead style. House style: Calibri font; name in dark blue `1F3864` bold ~17pt and ALL-CAPS; **Title Case** dark-blue `1F3864` section headers (NOT all-caps — verified 2026-06-24, the current Calibri resumes have no all-caps formatting on headers; only the name is all-caps), each with a blue `2E5496` bottom-border rule; gray `595959` contact line and dates; clickable LinkedIn/GitHub; a comfortably full single page (~90% fill, not a bullet wall — see the resume density target in MEMORIES) (summary, education/certs, experience, a Technical Support and Lab Experience section, 3 projects, 4 skills rows). Root cause of the JC-521435 miss (2026-06-18): a resume was drafted from scratch off the base file with generic styling because no finished submitted resume was opened first. The general pattern to kill: starting from raw material or scratch when a proven finished artifact already exists in the project.
14. **Don't re-render for trivial edits; batch them (adopted 2026-06-20).** A one-word or one-phrase change does not need a full rebuild + PDF render + folder copy + re-verify + re-present cycle. For text-only swaps that can't change length, make the edit and move on. Only run the LibreOffice render to re-check page count when an edit could actually change the length (added/removed sentences). When Uriah is in a reviewing groove giving several changes in a row, collect them and rebuild once, not once per change. (This session burned ~20 build cycles on the SOQ, many for single words.)
15. **Run the pre-submit audit BEFORE the first full review, not piecemeal (adopted 2026-06-20).** See `PRE_SUBMIT_CHECKLIST.md` in the project root. Run that single structured pass (claim/honesty audit, anti-AI/format checks, cert-date sanity, acronym-once, page/font/margin spec) up front so issues like a fabricated-sounding claim, an M365 stretch, AI-authored-code phrasing, or a future-dated cert surface in ONE pass instead of across many review rounds. Acronyms are spelled out ONCE per document (first use only), not once per answer — Uriah corrected this on JC-522217. **The deterministic checks are now mechanized — run them, do not hand-roll them (added 2026-06-24).** `python3 tools/pre_submit.py "<JC folder>" --soq-pages N` chains `verify_doc.py` (font/size/pages/margins/dashes/colons/acronym-once on the SOQ and resume), `check_678.py` (the 678 duties `.txt` against the ~1,000-char clip, en/em dashes, and mid-sentence colons), and `check_cross_doc.py` (no copy-paste across resume, SOQ, and 678). Save the finalized 678 duties block into the JC folder as `Uriah_Raffer_STD678-duties_JC-######.txt` so the gate can read it (also a clean record of the exact submitted duties wording). The tools cover only the mechanical items; the claim/honesty audit stays a human read.
