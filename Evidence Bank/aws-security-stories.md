Verified from his four AWS repos (aws-ha-infra, terraform-aws, ansible, aws-sso-project, all personal/homelab, not production) plus his own words. **DEFENSIBLE prompt-2 story (a "security issue I resolved"):** he hardened his AWS lab access model on two fronts. (1) Eliminated standing SSH (keypairs, open port 22, bastion) and moved to SSM Session Manager, so access requires temporary credentials from an authorized user, no open inbound, no keys to leak; activity auditable via CloudTrail. (2) Separation of duties / least privilege on identities: his day-to-day IAM user (mrpocket2726) actually carries AdministratorAccess via an "Admins" group (NOT "all rights except admin" - that was his misremembering, corrected 2026-06-20 from a console screenshot). He intentionally uses that admin IAM user instead of root for daily work, per best practice, and keeps root reserved for the handful of account-level tasks only root can do. The real fix in the story: he had been pointing his Terraform automation at that broad admin identity with long-lived credentials, and he moved automation onto a dedicated role scoped to just Terraform's needs, backed by AWS SSO issuing temporary credentials. NOTE for honesty: the daily user still has AdministratorAccess (he only carved out the automation role), so frame the win as "scoped the automation," not "locked down the daily identity." Also: admin != root - root-only tasks include changing root's own credentials, closing the account, restoring a locked-out IAM admin, billing-console access, and break-glass recovery of deny-all S3/SQS policies; this is WHY not using root daily is best practice. Lesson he states himself: keep security a default priority in whatever he builds. This is his real reasoning and he can defend every beat. **IMDSv2 - NOW DEFENSIBLE as of 2026-06-20 (updated; was previously flagged as off-limits).** He enforced IMDSv2 (`http_tokens = "required"`) and originally could NOT explain why IMDSv1 was exploitable. On 2026-06-20 he was taught the mechanism and demonstrated he can now explain it cold: IMDSv1 serves the instance's temporary IAM role credentials over an unauthenticated GET to 169.254.169.254, so an SSRF flaw in an on-box web app (e.g. a URL-fetch/preview box) can be tricked into retrieving those credentials with no host compromise - this is the Capital One 2019 breach class. IMDSv2 requires a PUT to obtain a session token plus a custom request header (`X-aws-ec2-metadata-token`) on every call; SSRF gives an attacker control of a URL but not the HTTP method or headers, so the token flow is unreachable, and the token response uses an IP hop limit of 1 so it can't be relayed off the instance. `http_tokens=required` rejects v1 entirely. He can speak to method+header as the two things SSRF can't fake. So IMDSv2/SSRF is now a usable lead story too, not just the SSH-to-SSM/least-privilege one. (Still: confirm he is comfortable on the day before featuring it.) Other real, citable AWS security details if needed: RDS encrypted at rest, security groups with zero inbound on private SG, Ansible Vault for secrets at rest, scoped IAM on the route-healer Lambda (ec2:ReplaceRoute only).
